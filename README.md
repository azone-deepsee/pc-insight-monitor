# PC Insight Monitor

**α版 v1.1.1** — USB / COM トラブル調査用のリアルタイム監視ツール

現場PCでバラバラに確認していた USB・COM・Windowsイベントログ・QRツールの接続ログを、**1本のタイムライン** にまとめて表示します。

---

## 特徴

- **サーバ不要** — Webサーバや exe は使いません
- **Python インストール不要** — ポータブル Python を同梱してファイルサーバから実行
- **QRツール改修不要** — 既存の USB 接続 CSV ログを取り込んで統合表示
- **調査時に手動起動** — 常時バックグラウンド監視は将来対応（α版は調査用）

---

## 動作環境

| 項目 | 要件 |
|------|------|
| OS | Windows 10 / 11（64bit） |
| 権限 | 一般ユーザー（管理者不要な場合が多い） |
| ネットワーク | ファイルサーバからフォルダ実行可能であること |
| その他 | PowerShell 実行可 |

## クイックスタート

### 現場PC（調査時）

1. ファイルサーバ上の `pc_insight_monitor` フォルダを開く
2. **`run.bat`** をダブルクリック
3. **「監視開始」** をクリック
4. 現象を再現し、[現場調査ガイド](#現場調査ガイド) に沿って確認
5. 終了時にウィンドウを閉じ、CSV ログを保管

### 開発PC（初回セットアップ）

配布用フォルダを作る前に、開発PCで **1回だけ** 以下を実行します。

```bat
setup_portable.bat
```

これにより `python\` フォルダに Python 埋め込み版と依存パッケージが入ります。  
完了後、フォルダ一式をファイルサーバへ配置してください。

## QRツールのログ連携

QRツールが出力している USB 接続/遮断 CSV を、調査時にタイムラインへ統合できます。

### 設定方法

`config.json` を編集します。

```json
{
  "qr_log": {
    "enabled": true,
    "directory": "D:\\Logs\\QR",
    "pattern": "*.csv"
  },
  "monitoring": {
    "poll_interval_sec": 2,
    "ping_target": "8.8.8.8",
    "enable_system_metrics": true,
    "enable_network_metrics": true,
    "enable_gpu": true
  }
}
```

| キー | 説明 |
|------|------|
| `qr_log.directory` | QRツールのログフォルダパス |
| `qr_log.pattern` | 取り込むファイル（既定: `*.csv`） |
| `monitoring.ping_target` | 疎通確認先（社内ゲートウェイ等に変更推奨） |
| `monitoring.enable_system_metrics` | CPU / メモリ / GPU 監視 |
| `monitoring.enable_network_metrics` | ネットワーク I/O・Ping 監視 |

### 取込手順

1. `config.json` にログフォルダを設定
2. アプリを起動
3. **「QRログ取込」** をクリック

接続・遮断を示すキーワード（接続、遮断、connect、disconnect など）を含む行を自動判別します。  
CSV形式が特殊な場合は [Issue](https://github.com/azone-deepsee/pc-insight-monitor/issues) で共有いただければパーサを調整します。

## ログの保存場所

調査セッションのログは各PCのローカルに保存されます（ファイルサーバには書き込みません）。

```text
%LOCALAPPDATA%\PCInsightMonitor\logs\session_YYYYMMDD_HHMMSS.csv
```

エクスプローラーで `%LOCALAPPDATA%\PCInsightMonitor\logs` と入力して開けます。

## 現場調査ガイド

現場PCで GitHub の README を見ながら調査を進めるための手順です。

### 調査開始時（現象再現の前）

1. `run.bat` で起動し、**「監視開始」** をクリックする
2. 上部ダッシュボードで **COM Unknown = 0** を確認する
3. 監視開始直後の10〜20秒は初期検出ログが出る。**この段階の Unknown はまだ異常とは限らない**（後述）
4. いつも通り操作して現象を再現する

### 平常時 — どのタブの何を見るか

#### 上部ダッシュボード（常に見る）

| 項目 | 見るポイント |
|------|-------------|
| **COM Unknown** | `0` なら正常。`1` 以上または ⚠ が出たら要注意 |
| **CPU / メモリ** | コードリーダー停止の直前に急上昇していないか |
| **Ping** | `NG` の場合、既定の `8.8.8.8` が業務PCでブロックされている可能性が高い（後述） |
| **タイムライン件数** | 監視中に数字が増え続けているか（止まっていたら監視が止まっている） |
| **状態** | 「監視中」になっているか |

#### タイムライン（調査の中心）

監視開始直後は USB デバイスの初回検出ログがまとめて出ることがある。

| 表示 | 意味 |
|------|------|
| `Status: OK`（通常色） | 問題なし |
| `Status: Unknown`（オレンジ） | **初回検出時はよくある**。変化がなければ無視してよい |
| `OK → Unknown に変化`（オレンジ） | **これが本当の異常サイン** |

**重要:** 初回検出の Unknown と、監視中の **Status 変化** は別物として見る。

#### グラフ（現象再現中に横目で見る）

| グラフ | 見るポイント |
|--------|-------------|
| **送信 / 受信スループット** | 通信断の瞬間に落ちるか |
| **CPU / メモリ** | アプリフリーズ・リソース枯渇の兆候 |
| **Ping** | 社内IPに設定していれば、ネットワーク断のタイミングと重なるか |

#### あまり見なくてよいタブ（平常時）

| タブ | 用途 |
|------|------|
| **COM一覧 / USB一覧** | 今の状態確認。変化があったときだけ見る |
| **イベントログ** | タイムラインと重複。詳細を深掘りするとき用 |
| **相関** | エラーが出てから使う |

### エラー発生時 — 確認するタブと解析手順

コードリーダー停止・COM切断などが起きたら、**次の順番**で確認する。

```text
① ダッシュボード（COM Unknown が増えたか）
      ↓
② タイムライン（何がいつ起きたか）
      ↓
③ 相関タブ（前後10秒の関連イベント）
      ↓
④ グラフタブ（同時刻にネットワーク / CPU 異常があったか）
      ↓
⑤ QRログ取込（あれば時系列を補完）
```

#### ① ダッシュボード

| 変化 | 疑う原因 |
|------|----------|
| COM Unknown が `0 → 1` 以上 | COMポート異常（直接サイン） |
| Ping が `NG` | ネットワーク断（社内IP設定時に有効） |
| CPU / メモリ急上昇 | PC側の負荷・リソース枯渇 |

#### ② タイムライン

**ソース絞込** を使って、イベントの発生順序を追う。

| 絞込 | 見ること |
|------|----------|
| **QRログ** | コードリーダーの接続 / 遮断の記録 |
| **EventLog** | Windows 側の Kernel-PnP などのシステムイベント |
| **COM** | `COM4 が OK → Unknown に変化` のような直接変化 |
| **USB** | USBハブやデバイスの状態変化 |

**重要度の色:**

| 色 | 意味 |
|----|------|
| 通常（黒） | 情報 |
| オレンジ | 警告（Unknown、疎通失敗など） |
| 赤 | エラー |

**よくあるパターン:**

```text
パターンA（USB / COM 起因）
  QRログ: disconnect
  → EventLog: Kernel-PnP [219]
  → COM: OK → Unknown

パターンB（ネットワーク起因）
  Ping NG / スループット急落
  → （COM / USB 変化なし）
  → アプリ側の通信タイムアウト

パターンC（PC 負荷起因）
  CPU / メモリ急上昇
  → 複数デバイスが同時に Unknown
  → その後回復 or 継続
```

#### ③ 相関タブ

**「相関ハイライト」** または **「相関を再分析」** を押すと、警告・エラーを起点に **前後10秒の関連イベント** がまとまって表示される。

| 用語 | 意味 |
|------|------|
| **トリガー** | 最初に起きた警告（例: QRログの disconnect） |
| **とどめ** | その後に起きた COM Unknown 変化など |

「何が先で、何が後か」をここで確認する。

#### ④ グラフタブ

タイムラインで異常時刻が分かったら、グラフで **同じ時間帯** を確認する。

| グラフの様子 | 疑う原因 |
|-------------|----------|
| ネットワークが落ちたが COM は正常 | 通信側の問題 |
| COM 変化と同時に USB イベント | デバイス / USB 側の問題 |
| CPU / メモリだけ異常 | PC リソースの問題 |

#### ⑤ QRログ取込

QRツールのログがある場合、**現象再現後** に「QRログ取込」を実行してタイムラインへ統合する。  
アプリ側の認識と Windows 側の認識のズレを確認できる。

### 現場チェックリスト

**調査開始時**

- [ ] 現象再現の **前** に「監視開始」を押した
- [ ] ダッシュボードで COM Unknown = 0 を確認した
- [ ] 初期検出ログが落ち着くまで10秒待った

**現象発生時**

- [ ] COM Unknown の数字が変わったか確認した
- [ ] タイムラインで最後の数件の **時刻とソース** をメモした
- [ ] 「相関」タブで関連イベントを確認した
- [ ] 「グラフ」タブで同時刻のリソース / ネットワーク変化を確認した

**調査終了時**

- [ ] ローカルの CSV ログを保存した
- [ ] 必要なら QRログを取り込んだ

### Ping が NG と表示される場合

既定の `8.8.8.8` は業務PCのファイアウォールでブロックされていることが多い。  
**プロキシの影響ではなく、ICMP や外部通信の制限** が原因のことが多い。

`config.json` の `monitoring.ping_target` を、社内で必ず応答する IP（ゲートウェイやファイルサーバなど）に変更する。

```json
"monitoring": {
  "ping_target": "192.168.x.x"
}
```

Ping 監視が不要な場合は `enable_network_metrics: false` に設定できる。

---

### 読み方の例

```text
15:59:58  QRログ      disconnect   COM4 遮断
16:00:00  EventLog    Kernel-PnP   [219] デバイス構成変更
16:00:01  COM         port         COM4 が OK → Unknown に変化
```

この順序なら、「QRツールが先に遮断を検知 → Windows がデバイス変更を記録 → COM が Unknown に落ちた」と読める。

## トラブルシューティング

### setup_portable.bat が 2/4 で失敗する

**症状:** `[2/4] Python をポータブルフォルダへインストール...` の後に「Python のインストールに失敗しました」と表示される。

**原因:** 開発PCに **Python 3.12 が既にインストールされている** と、公式インストーラが `TargetDir` を無視し、指定フォルダへ配置しない既知の挙動があります。

**対処（推奨）:**

1. 開発PCに [Python 3.12](https://www.python.org/downloads/) が入っていることを確認する（未導入ならインストール）
2. **最新版の `setup_portable.bat` を再実行**する（自動で「既存 Python 3.12 のコピー」方式に切り替わります）
3. 完了後、`python\python.exe` があることを確認してからファイルサーバへ配置する

**補足:** v1.1.1 以降の `setup_portable.bat` は、既存 Python 3.12 がある場合はインストーラを使わずコピーします。

### 起動しない

1. **`diagnose.bat`** を実行し、どこで失敗しているか確認
2. `python\python.exe` があるか確認 → なければ開発PCで `setup_portable.bat` を再実行
3. **`python` フォルダごと** ファイルサーバへ再配置（GitHub の clone だけでは起動できません）
4. ファイルサーバ（UNCパス）から起動できない場合、ローカルにコピーして試す
5. エラーに `tkinter` と出る場合 → 旧版の埋め込み Python では GUI が動きません。`setup_portable.bat` を再実行してください（v1.1 以降は tkinter 同梱）

### USB名が文字化けする

- α v1.0 では cp932 対応済み。再発する場合は OS 言語設定とあわせて Issue を報告してください

### イベントログが表示されない

- `pywin32` が正しくセットアップされているか確認（`setup_portable.bat` を再実行）
- 起動**後**に発生したイベントのみ表示されます（過去ログは対象外）

### QRログが取り込めない

- `config.json` の `directory` パスが正しいか確認
- CSV に日時列があるか確認（`YYYY-MM-DD HH:MM:SS` 形式など）
